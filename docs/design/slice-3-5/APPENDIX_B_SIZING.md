# Appendix B — Sizing: row counts, storage, load times

Part of [DESIGN.md](DESIGN.md) §2.8–§2.10. B.1–B.4 size the **full grain** (`ci`, `full`); **B.5 sizes `fleet15k`** from per-row sizes measured on PostgreSQL 16.

## B.1 Model

The estimate simulates the fleet model of DESIGN §2.2–§2.3 at the account
level (Python 3.11, seed 42) and counts FOCUS rows per day at the
full grain of D-01 (`ci` and `full`). It is an **estimate for sizing**, not the
generator; the generator (PR 3-1) measures the real numbers, and PR 3-4
records them.

| Parameter | Value |
|---|---|
| Account monthly spend | log-normal, median $800, σ = 1.8 (log scale) |
| Services per account | `round(3 + 4·log10(1 + spend/100) + N(0, 2))`, clamped to 1…80 |
| Regional services | 70 %; a regional series spends in 1 region, +1 with probability 0.35 each, max 6 |
| Commitment accounts | 60 % of accounts above $20 k/month, 10 % of the rest; their top 3 services carry an extra Committed row per region |
| Untagged remainder row | 30 % of account-services |
| Dynamic (spot) split | 8 % of account-services, one extra row per region |
| Monthly non-usage rows | 1 tax + 1 recurring fee per account; credits on 15 % of accounts; 3 purchase-related rows per commitment account |
| Stored bytes per fact row | 0.6 KB (target for lean extra columns) to 1.03 KB (measured on the public FOCUS 1.0 sample, Slice 2b EVIDENCE §6, of which 0.67 KB `extra_columns`) |
| Load rates | 20 k rows/s (Slice 1: 200 k narrow synthetic rows in ≈ 10 s, per-row trigger included) and 6 k rows/s (Slice 2b: 10 k real-shaped rows in 1.6 s end to end); **neither measured at tens of millions of rows** |
| Rollup bytes per row (incl. primary-key index) | 160–190 B for `cost_daily` **(assumption)** |
| Resources per series (charge-level comparison only) | 25 **(assumption)** |

The `ci` profile uses 4 periods (0.24 M rows); `full` uses 13 (D-02).
`fleet15k` uses a different grain and is sized in B.5.

**Generated bytes (assumption):** ≈ 350–450 B of CSV text per row, ≈ 70 B
gzipped (the rows of one series are highly repetitive), so ≈ 30 GB of text
streamed and **≈ 5–6 GB of gzip objects** for `full`; evidence capture
stores the same bytes again (≈ 11 GB in local S3 in total).

**Disk for a `full` run (assumption):** facts 47–81 GB + rollups and
forecast tables ≈ 12 GB + WAL and checkpoint headroom ≈ 10 GB + local S3
≈ 11 GB + generator output ≈ 6 GB ⇒ **≥ 150 GB free** recommended.

## B.3 Consequences

1. **Charge-level or resource-level generation is not feasible locally**
   (1.45–34.8 B rows); the aggregated daily grain is (D-01).
2. **`full` is an on-demand run on the owner's environment** (D-03, OA-1):
   neither CI nor this container class (≈ 10 GB free) can hold 47–81 GB.
3. **D-09 must be reviewed** (DESIGN F4): ≈ 6 M rows per month crosses its
   "a few million rows" trigger. At 10–18 µs per row, the per-row trigger
   costs ≈ 13–24 min over 78.6 M rows.
4. **Parallel sources:** 36 sources (one per billing account) can sync in
   parallel; the lease is per source. 4 in parallel is the planned setting;
   the measured speed-up is a PR 3-4 output.
5. **Batch sizes stay inside the worker's limits:** the largest billing
   account holds ≈ 15 % of rows, ≈ 0.9 M rows per monthly batch (limit
   20 M); files are split at ≤ 500 k rows.
6. **Rollups are ≈ 5× narrower than facts** and are what the analytics job
   and the API scan repeatedly; facts are read once per published batch.

## B.4 Reproducing the estimate

Python 3 standard library only. SHA-256 of the script as run:
`aa166e858c90cd2676e3bbaafe7ee3a93b1f656d917cc226ed88695d10469ca3`.
Save it as `sizing.py` and run `python3 sizing.py 150`, `1500` and `15000`.
It is a design aid, not part of the product, and is not committed as code.

```python
import random, math, statistics, sys
random.seed(42)
N = int(sys.argv[1]) if len(sys.argv) > 1 else 15000
# account monthly spend, lognormal heavy tail
spend = [math.exp(random.gauss(math.log(800), 1.8)) for _ in range(N)]
tot = sum(spend); s = sorted(spend, reverse=True)
print("accounts", N)
print("fleet monthly spend $%.1fM" % (tot / 1e6), "median %.0f p90 %.0f p99 %.0f max %.0f" % (statistics.median(spend), s[int(.1 * N)], s[int(.01 * N)], s[0]))
print("top1%% share %.1f%%  top10%% share %.1f%%" % (100 * sum(s[:N // 100]) / tot, 100 * sum(s[:N // 10]) / tot))
rows_day = 0; series = 0; usage_series = 0
svc_counts = []
commit_accts = 0
for m in spend:
    k = max(1, min(80, round(3 + 4 * math.log10(1 + m / 100) + random.gauss(0, 2.0))))
    svc_counts.append(k)
    series += k
    commit = (m > 20000 and random.random() < 0.6) or random.random() < 0.1
    commit_accts += commit
    for j in range(k):
        regional = random.random() < 0.7
        r = 1
        if regional:
            while r < 6 and random.random() < 0.35:
                r += 1
        rows = r
        if commit and j < 3:
            rows += r      # committed + standard split for top services
        if random.random() < 0.3:
            rows += 1      # untagged remainder row
        if random.random() < 0.08:
            rows += r      # dynamic/spot split
        rows_day += rows; usage_series += r
print("services/account mean %.1f median %d p99 %d max %d" % (statistics.mean(svc_counts), statistics.median(svc_counts), sorted(svc_counts)[int(.99 * N)], max(svc_counts)))
print("commit accounts", commit_accts)
print("account x service series", series, " account x service x region series", usage_series)
monthly_other = N * 1 + int(.15 * N) + commit_accts * 3 + N
rows_day_total = rows_day + monthly_other / 30.4
print("usage rows/day %d ; other rows/month %d ; total rows/day %.0f" % (rows_day, monthly_other, rows_day_total))
for days, label in [(120, '120 days'), (212, '7 periods'), (395, '13 periods')]:
    r = rows_day_total * days
    print(label, "rows %.2fM" % (r / 1e6), "storage @0.6KB %.1f GB  @1.03KB %.1f GB" % (r * 0.6 / 1e6, r * 1.033 / 1e6),
          "load @20k/s %.0f min  @6k/s %.0f min" % (r / 20000 / 60, r / 6000 / 60))
print("month rows (30.4d) %.2fM" % (rows_day_total * 30.4 / 1e6))
# rollups: bytes per row include the primary-key index (assumption)
for days in (395,):
    rr = series * days
    print("rollup acct x svc x day rows %.1fM, @130B %.1f GB" % (rr / 1e6, rr * 130 / 1e9))
    rr2 = usage_series * days
    print("cost_daily (acct x svc x region x day) rows %.1fM, @160-190B %.1f-%.1f GB" % (rr2 / 1e6, rr2 * 160 / 1e9, rr2 * 190 / 1e9))
# charge level, for comparison (assumption: 25 resources per series)
res_per_series = 25
print("charge-level resource x hourly over 395d: %.1fB rows" % (usage_series * res_per_series * 24 * 395 / 1e9))
print("resource x daily over 395d: %.2fB rows" % (usage_series * res_per_series * 395 / 1e9))
```

## B.5 `fleet15k`: sizing from measured row sizes

### B.5.1 The constraint

`fleet15k` must hold **all 15,000 accounts** and fit comfortably in
**≤ 6 GB in total**: object storage, Postgres facts, rollups, forecasts and
indexes (orchestrator decision, 2026-10-04). The container class it runs in
has ≈ 10 GB free disk, 4 CPUs and 15 GB RAM.

### B.5.2 What was measured (2026-10-04)

On an **ephemeral `postgres:16` container** (local Docker image, no volume,
removed afterwards), with the scripts in B.5.6:

| Object | Shape | Measured bytes per row (total, incl. indexes) | of which heap | of which `extra_columns` |
|---|---|---|---|---|
| `cost_facts`, `fleet15k` row (lean) | `cost_facts`' exact columns and primary key; 10-decimal money; `Tags` with `business-unit` and `cost-center` only; `ChargeFrequency`; `PricingCategory` on 1 row in 10 | **554.2** | 409.6 | 100.5 |
| `cost_facts`, first-revision minimal row | as above, plus `env` tag and `PricingCategory` on every row | 599.8 | 455.1 | 147.0 |
| `cost_daily`, narrow (5 measures, primary key only) | Appendix D §D.1 | **217.0** | 117.0 | — |
| `cost_daily`, wide (13 measures, PK + btree + BRIN) | first-revision sketch | 317.3 | 167.2 | — |

Each measurement used 400,000 rows. Not measured: the CHECK constraints,
foreign keys and triggers of the real table add no stored bytes; TOAST is
not involved at these row widths.

**Gzip bytes per row:** 19.4 B measured on 200,000 synthetic CSV rows with
the `fleet15k` column set (B.5.6, `csvsize.py`); **30 B is used** below
because real generator output has more distinct values (e.g. billed ≠
effective on committed rows). Objects are counted **three times**: the
generator's output directory, the source bucket and the evidence bucket.

### B.5.3 Arithmetic

Same account model and seed as B.4. Each account keeps its top 2 services as
individual series (top 4 for the largest 5 % by spend) and sums the rest into
one `Other services` series; non-usage rows (tax, recurring fee, credits,
commitment purchases) are added monthly.

| Quantity | Value |
|---|---|
| Accounts | **15,000** (all) |
| Usage series (account × service, incl. `Other services`) | **45,067** (3.00 per account); the full mix would be ≈ 107 k |
| Non-usage rows per month | 37,665 |
| Span | 4 billing periods of 31, 30, 31, 30 days = **122 days** |
| Fact rows per day / total | ≈ 46.3 k / **≈ 5.65 M** |
| Series-days (rollup rows) | ≈ 5.50 M |
| Postgres facts (554 B/row) | **3.13 GB** |
| `cost_daily` rollup (217 B/row) | **1.19 GB** |
| Objects (30 B/row × 3 copies) | **0.51 GB** (0.34 GB once the generator's local copy is removed after a verified upload) |
| Forecast state (2 runs), aggregate forecast points, `cost_daily_scope`, `billing_daily`, `account_dim`, anomalies | **≈ 0.34 GB** (assumption, deliberately generous) |
| **Total** | **≈ 5.17 GB** (≈ 5.0 GB without the local copy) |
| Headroom to 6 GB | ≈ 0.8–1.0 GB, kept for WAL (`max_wal_size` bounded, e.g. 256 MB), temporary files and the control tenant (`ci`-sized, < 0.3 GB) |
| Single-worker load at 20 k / 6 k rows/s | **4.7 / 15.7 min** (D-06 trigger: 60 min) |

**Honest reading of the headroom.** 5.2 GB inside a 6 GB ceiling is
comfortable only if the measured sizes hold. PR 3-4 measures the real total.
If it exceeds 5.5 GB, the escalation options, in order, are: remove the
generator's local copy after upload (−0.17 GB); keep 2 individual services
for every account (−0.16 GB, B.5.6 variant); shorten to 3 periods (−1.3 GB,
but only 1–2 origins at the 30-day horizon). **The account count is never
reduced.**

### B.5.4 What does not fit, and why

With the same measured per-row costs, keeping **every** account × service
series (≈ 107 k):

| Span | Fact rows | Total | Verdict |
|---|---|---|---|
| 4 periods (122 d) | 13.24 M | **11.37 GB** | does not fit |
| 3 periods (91 d) | 9.87 M | 8.48 GB | does not fit |
| 2 periods (61 d) | 6.62 M | 5.68 GB | fits on paper, no headroom, and **fails the backtest requirement**: after the 56 days weekly seasonality needs, no month is fully held out |

So with all 15,000 accounts at daily grain, the full service mix cannot fit
6 GB at any span that supports the required backtest. What fits is all
15,000 accounts with the **service axis reduced** to the top services plus
an `Other services` series, which is `fleet15k`.

### B.5.5 What `fleet15k` gives up

- **Service granularity** below each account's top 2 (top 4) services: the
  tail is one series, so an anomaly confined to a tail service is diluted.
  The generator therefore places every injected anomaly and every new
  service on an individual series; the tail is scored like any leaf and
  reported separately.
- **Region**: no region dimension, so `new_region` and region root causes
  are assessed on `ci` and `full` only.
- **Pricing and tag splits**: commitment effects and tagging loss are
  whole-series switches.
- **Span**: no 90-day horizon evaluation, and too few origins for
  per-series interval quantiles (cohort-pooled only).

DESIGN §2.8 lists, target by target, what `fleet15k` can and cannot assess.

`fleet15k.py`:

```python
import random, math, sys
# fleet15k sizing: account x service x day, top services individually + one "Other services" series.
# Same account model and seed as sizing.py (Appendix B.4).
random.seed(42)
N = 15000
spend = [math.exp(random.gauss(math.log(800), 1.8)) for _ in range(N)]
cut = sorted(spend, reverse=True)[N // 20]          # top 5 % of accounts by spend
series = 0; full_series = 0; commit_accts = 0
for m in spend:
    k = max(1, min(80, round(3 + 4 * math.log10(1 + m / 100) + random.gauss(0, 2.0))))
    full_series += k
    keep = 4 if m >= cut else 2
    series += min(k, keep) + (1 if k > keep else 0)
    commit_accts += (m > 20000 and random.random() < 0.6) or random.random() < 0.1
billing_rows_month = N + int(.15 * N) + commit_accts * 3 + N   # tax, credits, purchases, recurring fee
DAYS = 122                                   # 4 billing periods: 31 + 30 + 31 + 30
FACT_B, ROLLUP_B, GZ_B = 554.2, 217.0, 30.0  # measured on PG16 (B.5), gzip estimate rounded up
rows_day = series + billing_rows_month / 30.4
facts = rows_day * DAYS
series_days = series * DAYS
gb = lambda b: b / 1e9
facts_gb = gb(facts * FACT_B)
rollup_gb = gb(series_days * ROLLUP_B)
objects_gb = gb(facts * GZ_B * 3)            # generator output + source bucket + evidence bucket
small_gb = gb(series * 400 * 2 + 15000 * 200 + 2e6 * 150)   # forecast state x2 runs, account dim, aggregate points
print("full-mix series %d ; fleet15k series %d (%.2f per account)" % (full_series, series, series / N))
print("billing rows/month %d ; fact rows/day %.0f ; fact rows %.2fM ; series-days %.2fM" % (billing_rows_month, rows_day, facts / 1e6, series_days / 1e6))
print("facts %.2f GB ; rollup %.2f GB ; objects %.2f GB ; forecasts+dims %.2f GB ; total %.2f GB" % (facts_gb, rollup_gb, objects_gb, small_gb, facts_gb + rollup_gb + objects_gb + small_gb))
print("load @20k rows/s %.1f min ; @6k rows/s %.1f min" % (facts / 20000 / 60, facts / 6000 / 60))
# alternatives, same per-row costs
for label, s, d in [("full service mix, 4 periods", full_series, 122), ("full service mix, 3 periods", full_series, 91),
                    ("full service mix, 2 periods", full_series, 61)]:
    f = (s + billing_rows_month / 30.4) * d
    tot = gb(f * FACT_B) + gb(s * d * ROLLUP_B) + gb(f * GZ_B * 3)
    print("%s: fact rows %.2fM, total %.2f GB" % (label, f / 1e6, tot))
```

import gzip, io, random
random.seed(7)
cols = ["BilledCost","EffectiveCost","BillingCurrency","BillingPeriodStart","ChargePeriodStart","ChargePeriodEnd",
        "ProviderName","BillingAccountId","SubAccountId","ServiceName","ServiceCategory","ChargeCategory",
        "ChargeClass","ChargeFrequency","PricingCategory","ResourceId","Tags"]
buf = io.StringIO()
buf.write(",".join(cols) + "\n")
N = 200000
# rows ordered as the writer would: by day, then account, then service
for i in range(N):
    acct = i // 4 % 15000
    day = 1 + (i // 60000) % 30
    v = random.random() * 900
    row = ["%.10f" % v, "%.10f" % v, "USD", "2026-05-01 00:00:00",
           "2026-05-%02d 00:00:00" % day, "2026-05-%02d 00:00:00" % (day + 1),
           "SyntheticAWS", "9991%08d" % (acct % 36), "9990%08d" % acct,
           "Synthetic Service %02d" % (i % 60), "Compute", "Usage", "", "Usage-Based",
           "Committed" if i % 10 == 0 else "", "",
           '"{""business-unit"":""bu%02d"",""cost-center"":""cc%03d""}"' % (acct % 12, acct % 400)]
    buf.write(",".join(row) + "\n")
raw = buf.getvalue().encode()
gz = gzip.compress(raw, 6, mtime=0)
print("csv bytes/row %.1f  gzip bytes/row %.1f" % (len(raw) / N, len(gz) / N))
