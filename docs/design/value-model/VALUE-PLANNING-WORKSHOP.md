## Purpose and journey

Named enterprise participants complete a prepared KPI and value-planning exercise in one to two working days; this is the workshop duration, not an implementation deadline. The outcome is an approved **planning business case**, not proof of realized benefit.

An authorized member creates a workshop bound to a project, assigns existing authorized members as sponsor, author, reviewer or Finance, and uploads CSV/XLSX or enters inputs manually. Participants inspect suggested mappings, explicitly accept a mapping revision, resolve formula findings, validate and calculate on the server, explore scenarios and graphs, resolve comments, approve an exact revision, and publish the immutable original business case. Existing identity, tenant, engagement authorization, and formula engine are reused. Outsider invitations and email delivery are out of scope unless an existing secure membership mechanism supports them. No shared token is exposed to the browser.

## Model and persistence proposal

Use reviewed tenant-scoped database tables with RLS and project/engagement authorization for workshops, participant assignments, uploads and private object references, mappings, immutable input/evidence snapshots, model revisions, scenario results, comments, review requirements, signoffs, publication packages and audit events. Derive tenant and actor from the authenticated session. A revision identifies exact inputs, accepted mappings, definition versions and digests, formula-engine version, rate assumptions and versions, scenarios, evidence references, and a canonical content digest. Use content hashes for uploaded artifacts and snapshots; never treat a client-supplied digest as proof of content.

Every object and download requires a fresh authorization decision, including membership revocation. Private evidence storage uses existing tenant-scoped content-addressed keys; no arbitrary client paths or URLs. Retention and deletion must be bounded by an approved organization policy, including legal holds, evidence dependencies and audit retention; the current evidence store has no delete API, so this is not yet satisfied. No raw file content, financial values or prompts in logs by default. Audit actor, action, resource, time, outcome and correlation ID without secrets or raw data.

Use monotonic revisions and compare-and-swap on material edits. Scope idempotency keys to tenant, workshop, actor and operation; bind them to a request digest, reject reuse with different content, and return the original result for a duplicate. Publication locks the revision, rechecks authorized assignments, blockers, exact-digest approvals and results, writes the immutable package and audit record, and changes state in one transaction. Duplicate or concurrent requests must not create multiple originals. Storage of the artifact and database commit needs a reviewed staged-object/outbox or equivalent recovery protocol; do not claim atomicity across systems without one. A restarted service reads durable state, not `/tmp`, localStorage or an in-memory registry.

## Inputs, upload and mapping

The downloadable Ratio template and manual entry use: input ID, description, value, unit, optional currency, period start/end, scope/segment, source reference, basis (`assumed`, `projected`, `observed`), verification state, and scenario. Preserve CSV decimal text and XLSX lexical decimal precision where actually present; never manufacture precision lost by an XLSX producer. Empty, missing and zero are different. Values, units, source and verification remain visible to reviewers. Map workshop basis explicitly to the engine's existing `assumption`, `forecast`, `observed`; verification is independent of basis. For ordinary observations the engine's `measured` label requires an allowed source and verification reference, not independent verification of that reference. For `kpi_result` inputs and value-case terms the current engine instead trusts the nested result's supplied status before checking basis. A workshop adapter must resolve that result from trusted records, verify its value and scope, and apply the weakest status including the input basis; this is not implemented. Approval does not promote an assumption to measured.

Proposed conservative defaults, subject to security review and configurable only downward at deployment: 10 MiB compressed upload, 50 MiB total expanded data, 100:1 expansion ratio, 20 sheets, 10,000 rows per sheet, 100,000 populated cells total, 4,096 characters per field, 1,000 characters per formula, and 30 seconds processing time. Enforce limits during streaming and decompression, before allocating or processing the full file, with worker isolation, resource limits and cancellation. Reject invalid extension/content combinations, encrypted and macro-enabled workbooks, malformed archives, duplicate or unsafe archive paths, external links and dependencies, oversized XML and unsupported encodings. Explicitly surface hidden sheets/rows and dependencies as review findings rather than silently dropping them.

Workbook values, formula text and cached results are untrusted references. Never execute macros, links, code or spreadsheet formulas. Translate only expressions supported by the bounded Ratio engine, recompute on the server, and display unsupported expressions and discrepancies with source file, sheet, cell and hash. A reviewer must resolve or explicitly exclude each finding with a reason before use. Exported user-controlled cells must be neutralized against spreadsheet formula injection, including leading whitespace/control characters before formula prefixes. Supporting attachments are private evidence, not automatic numeric extraction.

Manual mapping must work without AI. If the existing server-side provider interface is available, Frank may suggest target mappings and explanations only after an authorized person approves the minimum selected source material. Do not send entire workbooks automatically. Treat all source text as untrusted, constrain and validate structured output, and do not invent rates, units, attribution or evidence. Show proposed target, source coordinates/hash, status and explicit user acceptance. Provider failure or absence is visible and leaves manual mapping available. Changes to source or mapping create new revisions and invalidate dependent results and approvals. Financial assumptions remain provisional pending appropriate approval; no finance register is created implicitly.

## Calculation and visual workspace

Use `ratio-formula/1` and exact rationals; round only for presentation using the definition's declared scale and half-even rule. Validate unit, currency, scope and period compatibility, input bounds, negative values and missing/null values. A zero denominator is unavailable, not zero or infinity. Respect the engine's bounded expression and conditional semantics, rather than promising general Excel compatibility. Explicitly model attribution and prevent overlapping benefit counts. Keep financial savings, capacity-equivalent benefit and nonmonetary KPIs separate. Authors and sponsors supply terms and assumptions, never final Value/cost, ROI or net benefit.

The workspace has inputs, model, results, comments/evidence and approvals. Render baseline versus planned KPI, benefit/cost waterfall, low/base/high scenarios and bounded sensitivity from server results only. Show cumulative benefit/cost only with explicit time-phased inputs; never invent monthly phasing. Do not mix currencies or periods. Scenario ranges are not confidence intervals and sensitivity is not causation. Each chart has “View calculation” and an accessible data table, including negative and unavailable states. Use existing typography, Display terminology and familiar controls, responsive phone and desktop layouts, keyboard/focus support, and loading, empty, error and permission states. Ask Frank must respect the same permissions and explicitly degrade when unavailable.

## Review and publication

Workshop states are Draft, In review, Changes requested, Approved and Published; definition approval remains a separate object with its existing lifecycle. Responsibilities `project_sponsor`, `kpi_author`, `kpi_approver`, and `finance_approver` are project scoped assignments, not new global roles. All invited authorized members may comment or acknowledge. Formal signoffs use server identity, time, scope, revision and digest; authorization and assignments are rechecked server-side. An ordinary nonfinancial definition requires one approver independent of its author. A financial valuation requires independent KPI and Finance approvers, distinct from each other and the author; sponsor acceptance is recorded separately, and the case sponsor cannot provide its Finance approval, consistent with the existing value-case lifecycle. Higher-risk extra review is permitted only within organization policy.

Material changes to inputs, mappings, evidence, definitions, formulas, rates, scenarios or review scope create a revision and invalidate dependent results and signoffs. Cosmetic metadata must be explicitly classified and kept outside the signed calculation digest; ambiguity is material. Unresolved blockers or stale signoffs prevent publication. The first approved forecast and issued case remain immutable. Later forecasts and corrections append with reasons, preserve the original comparison, and show separately approved restatements or “not comparable” when scope, period or definition changes. Preserve all artifacts required to reproduce issued results.

## Proposed API contracts

Following existing versioned routes and error conventions, propose `/api/v1` workshop resources for create/read, authorized participant list/add, bounded private upload and authorized download, mapping inspection/import and acceptance, input save, scenario calculation, comments/change requests, exact-revision signoff, publication and authorized published-package retrieval. Resource identifiers are opaque server-issued IDs; no user-supplied tenant, actor, role grants, SQL, file paths or URLs. Write requests carry expected revision and scoped idempotency key; signoff carries the displayed revision/digest, which the server verifies against stored canonical content. Conflicts return a redacted conflict response without overwriting. Validation errors identify fields but do not echo sensitive values. Session writes require the existing exact-origin and CSRF checks; apply request size limits, per-actor and tenant rate limits, and fail closed. Define schemas and route-level permission mapping in a separately reviewed contract change, not by silently changing stable contracts.

## Threat model

Assets include financial inputs, personal identities, source files, approvals and issued artifacts. Threats include cross-tenant/object access and insecure downloads; revoked or forged identities; author self-approval, dual-role misuse, stale/replayed signoffs and publication races; malicious archives, spreadsheet formulas and export injection; prompt injection and provider exfiltration; arbitrary paths/URLs and log leakage; accidental data loss or unauthorized artifact replacement. Mitigations are server-derived identity and object-level authorization, private storage, reviewed RLS and least privilege, digest/revision binding, transactional concurrency and idempotency, bounded isolated parsing, no execution, output validation, minimum explicit AI disclosure, redacted audit, and immutable versioned artifacts. These are requirements, not claims about the present code. Security review must include retention, object lifecycle, database access and the AI disclosure boundary.

## Migration, rollback and release gates

No workshop migration or privilege change is included. `docs/migrations/ledger.json` reserves 0005–0039. ADR-0001 §12 requires every lower reservation to be merged, released or retired before a higher migration and requires expand-only SQL, a manifest, database tests and schema-version pinning. ADR-0002 §8 also requires authorized tenant-scoped readers and reviewed privilege models before dependent paths. The owner/orchestrator must resolve the ledger and review RLS, least-privilege grants, membership-to-project policy and storage/retention before a durable workshop slice can merge. Do not bypass these gates with simulation SQLite or broaden grants.

When permitted, use an expand-only, ordered migration and manifest with tenant-scoped constraints, RLS and append-only guards, followed by application rollout. A rollback disables the new routes and reverts application code while retaining the expanded schema and issued artifacts; destructive down migrations are not assumed safe under the expand-only runner. If governance approves a reversible migration/test mechanism, exercise up/down/up on disposable databases and verify restoration and historical reproduction; otherwise record the exact limitation. Recovery must preserve the original published package and avoid orphaned staged objects.
